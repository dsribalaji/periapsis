# ADR-0003 — Restricted N-body: prescribed ephemerides, one integrated spacecraft

**Status:** accepted
**Date:** 2026-11-18

## Context

A mission designer needs the gravity of many bodies acting on a spacecraft. The obvious
implementation is a full N-body integrator: integrate every body and the spacecraft together,
each attracting each.

That is not what this app does, and the difference is worth stating precisely, because
"we do N-body" without qualification would be misleading.

## Decision

The planets follow **prescribed** ephemerides (JPL Table 1 Keplerian elements, evaluated at the
requested instant). Only the spacecraft is integrated, under the acceleration

```
a = Σ_i  −μ_i (r − r_i) / |r − r_i|³        (r_i from the ephemeris)
```

This is the **restricted** N-body problem: test particles in a field generated by bodies whose
motion is given.

## Why

1. **Accuracy.** A full numerical integration of the planets would be _worse_ than Table 1 over
   the app's time span, not better. Table 1 is fitted to DE ephemerides; a self-integrated
   planet set with point-mass Newtonian gravity drifts away from the real solar system because
   it omits the very perturbations (J₂, asteroid masses, relativity) that the fit absorbs.
   Reproducing the real positions is a solved problem; re-solving it badly is not progress.

2. **Cost.** Integrating nine massive bodies with the spacecraft multiplies the force
   evaluations by ten for no gain in spacecraft accuracy.

3. **Reproducibility.** Prescribed positions are a pure function of time. The spacecraft's
   trajectory therefore depends only on its own state and the epoch, which makes a scenario
   replayable and a test deterministic.

4. **Honesty about scope.** The app is a mission designer, not an ephemeris generator. Its time
   span is months to a few years, where the prescribed-field approximation is excellent.

The one real cost: this model cannot show a spacecraft measurably perturbing a planet. Nothing
in the app needs it to.

## Consequences

**Good:** force evaluation cost is linear in the number of bodies with no coupled state; the
spacecraft problem is a clean ODE the integrator can adapt to; trajectories are exactly
repeatable.

**Bad:** the field is not self-consistent — energy is not conserved for the spacecraft in any
meaningful global sense, and "energy drift" tests must be run in the two-body limit where the
field is static. That is why the integrator tests use a single central body. Momentum
conservation is likewise not a property of this system, so no test asserts it.

**Also:** patch-point discontinuities. When the dominant body changes, the acceleration is
discontinuous. The integrator must not straddle a patch point with a huge step, which is why
dominant-body selection is part of the propagation loop rather than a precomputation.

## Alternatives considered

- **Full N-body.** Rejected on accuracy and cost, above.
- **Two-body per SOI only (pure patched conics, no N-body).** Simpler and faster, but it cannot
  represent a trajectory that is genuinely influenced by two bodies near a patch point, and it
  makes Lambert-derived transfers look artificially exact. The restricted N-body path is the
  fallback that shows the truth.
- **Interpolated DE ephemeris file.** Much more accurate, but it needs a data file of
  megabytes and a licence question, for accuracy far beyond what a compressed 3D view and
  indicative delta-v can use. Noted as a future upgrade path.
